# Vercel deployment

## Services and routing

The root `vercel.json` defines `backend` and `frontend`. The root service from
the suggested configuration was a second detection of the same Python app,
so there is no `app` service. The backend root remains `.` because imports and
Python package metadata are relative to the repository root.

| Public path | Service | Purpose |
| --- | --- | --- |
| `/api/blob-upload` | frontend | Node function for Blob upload authorization/callbacks |
| `/api/*` | backend | FastAPI metadata, results, media, simulation, upload intents |
| Everything else | frontend | Vite assets and React navigation |

The frontend Node function calls the backend using its `BACKEND_URL` binding.
Vercel supplies this URL at runtime. It is never a `VITE_*` variable, a build
input, a fixed hostname, or a middleware dependency. Browser calls use the
public same-origin `/api` paths. Rewrites preserve the API prefix.

`backend.worker` is a private queue subscriber compiled from
`[[tool.vercel.subscribers]]` in `pyproject.toml`. It has no public rewrite.
Queue messages contain only the analysis ID; video bytes stay in private Blob
storage. There is no HTTP call from backend to a separate worker service, so
no additional service binding is needed.

## Connect infrastructure

1. Import the repository into one Vercel project with repository root `.`.
2. Connect a managed PostgreSQL database and configure `DATABASE_URL`, using
   the provider's TLS settings. No specific PostgreSQL vendor is required.
3. Create and connect a **private** Vercel Blob store. Configure
   `BLOB_READ_WRITE_TOKEN` for the frontend's upload-token handler and backend
   object operations. Do not expose it in a `VITE_*` variable.
4. Enable Vercel Queues for the project. The SDK uses the deployment's OIDC
   identity. The topic is `flowlab-video`; publishing uses region `iad1`.
   Keep previews and production on separate databases and Blob stores: queue
   deployment partitioning does not isolate a shared database or Blob store.
5. Install Python dependencies, load `DATABASE_URL` into the current shell,
   and run `python -m backend.scripts.migrate_hosted`. This additive command
   creates tables and indexes. Run it before sending requests. Application
   imports and subscriber discovery never connect to PostgreSQL during builds.
6. Keep `VITE_API_URL` unset. Never manually configure `BACKEND_URL`: it is
   generated by the binding. `FLOWLAB_HOSTED` defaults on when `VERCEL=1`;
   set `FLOWLAB_HOSTED=1` when exercising cloud storage outside Vercel.
7. The root `vercel.json` enables Fluid Compute and supplies
   `VERCEL_SUPPORT_LARGE_FUNCTIONS=1` through shared `build.env`, so the Python
   builder receives the opt-in even when no dashboard variable was added.
   This is a non-secret build flag. Vercel generally recommends dashboard
   variables over the legacy `build.env` key; it is used here to make this
   deployment requirement explicit in the repository. Active CPU must also
   be enabled on the Vercel project. Redeploy with
   the build cache disabled after changing the dependency selection. This
   vision stack exceeds the standard 500 MB Python limit even with CPU wheels;
   Large Functions support up to 5 GB. `maxDuration`, memory, and `excludeFiles`
   cannot raise that ceiling. Copying `.env.example` alone does not configure
   the cloud project. If the next build still reports a 500 MB maximum,
   verify `VERCEL_SUPPORT_LARGE_FUNCTIONS=1` under **Project Settings >
   Environment Variables** for the deployment's target environment, check
   Fluid Compute/Active CPU and Large Functions eligibility, and redeploy.
   Secure Compute and Static IP projects are not eligible for Large Functions.

   The dependencies use headless OpenCV/Ultralytics to avoid GUI OS libraries.
   `tool.uv.sources` selects CPU PyTorch for uv project installs. Vercel also
   detects `backend/requirements.txt`, which now declares the official CPU index
   directly. Vercel converts that into a uv index, whose default first-index
   resolution selects PyTorch packages from the CPU index ahead of PyPI.
   The verified Linux x86_64 resolution selected `torch==2.14.1+cpu` and
   `torchvision==0.29.1+cpu`, without CUDA runtime packages. `.python-version` pins the
   deployment to Python 3.12 at both the project and backend discovery roots.
   Validate the deployed model and OpenCV runtime as well. Existing local
   environments should be recreated rather than mixing GUI and headless
   OpenCV distributions, which both install the `cv2` module.

   A pip install uses its own index-resolution behavior; the Vercel fix relies
   on uv's first-index strategy. For a local GPU environment, install the
   project from `pyproject.toml` (`pip install .`) with the appropriate PyTorch
   build instead.

   The resolved Linux/Python 3.12 wheels contain
   about 1,235 MiB uncompressed in total, before function/runtime overhead.
   This is below the large-function ceiling, but above the standard ceiling;
   a successful cloud rebuild remains the final artifact-size check.
8. Run `vercel dev` from the repository root with the connected environment.
   Exercise a direct upload, its callback, queue progress, a region edit,
   media downloads, and deletion. Blob callbacks need a reachable URL; the
   browser also calls completion so local testing can finalize an upload.

The local CLI check detected both services and accepted the routing/binding
configuration. Startup stopped because this checkout's `.venv` has no `pip`.
Repair that environment (`.venv/Scripts/python.exe -m ensurepip --upgrade` on
Windows), install the runtime dependencies, and rerun `vercel dev` after
connecting the hosted environment. No live PostgreSQL/Blob/Queues integration
has been exercised yet.

Use deployment access protection for sensitive footage. This application has
no user accounts or per-user authorization. Upload intent tokens authorize a
single object and expire after an hour; they do not establish a user identity.
Internal binding calls bypass public deployment protection, while the public
API still exposes every analysis to anyone allowed into the deployment.
Verify that deployment protection allows Blob's signed completion callback to
reach `/api/blob-upload`; otherwise only the browser's completion request can
finalize the upload. Test the callback with the browser tab closed as well.

## Import existing local analyses

Stop the local API and finish any queued jobs first. Configure the destination
`DATABASE_URL` and private `BLOB_READ_WRITE_TOKEN`, then run:

```bash
python -m backend.scripts.migrate_hosted --import-local ./data
```

The command copies existing video/result files to private immutable Blob
objects and inserts analysis metadata in PostgreSQL. It leaves the local data
in place, skips the bundled demo and IDs already present at the destination,
and refuses to import a database with unfinished jobs. It does not run during
deployment. Use a destination dedicated to the intended environment.

## Failure handling and limits

The API only reports an upload accepted after publishing its queue message.
If publishing fails, retry completion with the same upload intent. Both Blob's
verified callback and the browser finalize uploads; queue idempotency keys
deduplicate those calls. The worker locks an analysis in PostgreSQL and skips
already completed or failed jobs, making duplicate deliveries safe.

Transient storage/processing exceptions are retried up to three deliveries.
Known detector/video errors become visible terminal errors. Progress is stored
in PostgreSQL, and a new API process never marks another worker's jobs as
orphaned. Hard timeouts cannot run cleanup; status polling marks processing
records with no update for ten minutes as errors so the UI can stop polling.

Workers allow 300 seconds, with a cooperative 240-second processing budget.
Long clips may need a larger plan-supported duration, chunked processing, or
an external long-running worker. Increasing the function duration also requires
adjusting the processing budget and stale-job timeout. Queue retention and
delivery limits still apply. A full provider integration and actual video
throughput must be verified before production use.

Temporary space holds model weights, source/annotated working files, and media
download copies. Normal completion removes working video files, and HTTP media
responses remove their copies after sending. A killed function can leave
scratch files until its instance is replaced. Account for both video copies
and model weights within the platform's temporary-disk and memory limits.

Results use immutable Blob URLs, with the current version referenced from
PostgreSQL. Region edits read that current reference on every request. Older
versions stay indexed and are deleted with the analysis; a failed Blob deletion
keeps references so deletion can be retried. Abandoned direct uploads and a
crash between a Blob write and its database reference can leave unreferenced
objects: include those in storage retention/maintenance procedures.
